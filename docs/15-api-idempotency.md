# API Idempotency

## 1. Overview

API Idempotency is a mechanism that ensures a client can safely retry the same request multiple times without creating duplicate business operations.

In distributed systems, network failures, client timeouts, application crashes, and retry mechanisms are common. Without idempotency, the same request may be processed multiple times, resulting in duplicate business records and inconsistent data.

The StreamHub Payment Service uses API Idempotency to guarantee that a business operation is executed only once, even if the client sends the same request multiple times.

---

# 2. Objectives

API Idempotency is responsible for:

- Preventing duplicate business operations.
- Supporting safe client retries.
- Preventing duplicate payment creation.
- Preventing duplicate refund creation.
- Improving reliability during network failures.
- Providing deterministic API responses.

---

# 3. Why Do We Need API Idempotency?

Consider the following scenario.

A customer initiates a payment.

```text
Customer

↓

Click Pay

↓

Payment Service

↓

Payment Created

↓

Response Sent

↓

Network Timeout
```

Although the payment is created successfully, the client never receives the response.

The client assumes the request failed and retries.

```text
Customer

↓

Click Pay Again

↓

Another Payment Created
```

Without idempotency, two payment records are created for the same business operation.

---

# 4. Problem Without Idempotency

```text
Client

↓

POST /payment-intents

↓

Payment Created

↓

Response Lost

↓

Client Retries

↓

Another Payment Created
```

Result

- Duplicate Payment Intent
- Duplicate Razorpay Order
- Duplicate Payment Record

---

# 5. Solution

The client generates an Idempotency Key.

Example

```http
POST /payment-intents

Idempotency-Key: 7fd9a8d3-f2ab-4b44-88d7-9bba4b0d3b11
```

The server stores the result of the first request.

When the same key is received again:

```text
Same Key

↓

Existing Request Found

↓

Return Previous Response

↓

Do NOT Execute Business Logic Again
```

Only one payment is created.

# 7. Idempotency Key

The Idempotency Key uniquely identifies a client request.

Example

```text
Idempotency-Key

↓

4a29c857-f5dc-4fd2-8fb5-4ef3bff8f4a1
```

Characteristics

- Unique
- Client Generated
- Sent in HTTP Header
- Reusable only for the same request

# 9. What Is Stored?

Typical information stored

| Field           | Purpose                    |
|-----------------|----------------------------|
| Idempotency Key | Unique request identifier  |
| Request Hash    | Detect modified requests   |
| Response Body   | Return identical response  |
| HTTP Status     | Preserve original status   |
| Created Time    | Auditing                   |
| Expiry Time     | Cleanup                    |

# 10. Why Store Request Hash?

Consider two requests.

First

```text
Key

ABC123

Amount

₹100
```

Second

```text
Key

ABC123

Amount

₹500
```

Same key

Different request.

This is not a retry.

The server detects this using the Request Hash.

```text
Request Hash

↓

Match?

↓

Yes

↓

Return Previous Response

↓

No

↓

409 Conflict
```

---

# 11. Where Should API Idempotency Be Used?

API Idempotency is recommended for operations that create or modify data.

Examples

```text
POST /payment-intents

POST /refunds

POST /payouts

POST /subscriptions
```

Not required for

```text
GET /payments

GET /refunds

GET /events
```

GET operations are naturally idempotent.

# 13. Difference Between API Idempotency and Webhook Idempotency

Although both prevent duplicate processing, they solve different problems.

## API Idempotency

### Problem

Duplicate requests are generated by the client.

Example

```text
Client

↓

POST Payment

↓

Timeout

↓

Retry
```

### Solution

The client includes an Idempotency Key.

```text
Idempotency-Key

↓

Return Existing Response
```

---

## Webhook Idempotency

### Problem

Duplicate webhook events are generated by Razorpay.

Razorpay guarantees **at least once delivery**.

Example

```text
payment.captured

↓

Delivered

↓

Timeout

↓

Delivered Again

↓

Delivered Again
```

### Solution

The Payment Service checks whether the business event has already been processed.

Example

```text
Payment Status

↓

SUCCESS?

↓

Yes

↓

Ignore Duplicate Webhook

↓

Return HTTP 200
```

---

# 14. Comparison

| Feature                | API Idempotency            | Webhook Idempotency                  |
|------------------------|----------------------------|--------------------------------------|
| Duplicate Generated By | Client                     | Razorpay                             |
| Trigger                | Client Retry               | Webhook Retry                        |
| Identifier             | Idempotency Key            | Business State or Gateway Event      |
| Purpose                | Prevent duplicate requests | Prevent duplicate webhook processing |
| Typical APIs           | POST, PUT, PATCH           | Webhook Endpoints                    |
| Example                | Payment Intent             | payment.captured                     |

# 17. Summary

API Idempotency ensures that a client retry does not execute the same business operation multiple times.

Webhook Idempotency ensures that duplicate webhook deliveries do not modify business data multiple times.

Together, these mechanisms make the StreamHub Payment Service resilient against retries, network failures, and duplicate event delivery, providing production-grade reliability and consistency.
